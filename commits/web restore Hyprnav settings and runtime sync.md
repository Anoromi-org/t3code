# Web restore Hyprnav settings and runtime sync

Expose Hyprnav in Settings with editable scoped bindings, validation, inheritance, grouped-project behavior, reset/save flows, and explicit runtime status.

Device-local defaults live on `/settings/hyprnav` (a device-only settings page, in the nav and settings search). Project overrides are a "Hyprnav" section inside upstream's scope-driven project settings (`/settings/projects?project=&machine=&checkout=`). At project scope the section edits the logical project group: in "same" mode a save writes every grouped checkout through `project.meta.update { hyprnav }`; in "separate" mode it lists the checkouts and opens the chosen one at checkout scope, where a save writes only that checkout. The grouping mode selector is available at both scopes. Overrides stay in `projection_projects.hyprnav_json`, not in upstream's project settings overrides, so the section renders its own inheritance row (device defaults vs. override, with a reset) using `SettingsSection`/`SettingsRow`. The legacy sidebar's project menu has a "Hyprnav settings" action that routes to the project scope; the default sidebar reaches the same section through Project settings.

Settings persist before best-effort desktop publication. Default changes publish to every inherited primary-local project; project changes publish project, every known worktree, and known thread scopes while leaving remote/browser projects unchanged. Publication refreshes Corkdiff-backed commands before ticket expiry, retries successful publications that omit requested scopes, and validates the contract's 255-character binding-name limit before persistence. Thread jobs are kept when publication history still holds slots a failed save may have applied, so a later save clears them even when the settings no longer differ. Duplicate records of one physical checkout share the retained record's overrides, so saves (which skip stale duplicates) and the active-thread runtime (which reads the retained record for a stale duplicate's threads) agree. `hyprnavPublicationTargetFromRequest` and `hyprnavPublicationScopesForRequest` return to `hyprnavRuntime.ts` with their settings-triggered consumer.

Awaited client-settings writes go through upstream's `persistClientSettingsUpdate` queue; the fork's separate durable-patch helper is gone. Functional updates of environment settings are serialized per environment and resolved against the last authoritative server response, so rapid provider-instance edits cannot drop one another. Provider instance edit/delete/reset, the add-provider dialog, device-local model preferences and favorites (settings panel and model picker), and legacy sidebar grouping overrides use functional updates. Upstream shared-settings fan-out, hosted-app availability warnings, and device-local model preferences are preserved.

## Reimplementation Sources

This intent reimplements fork commit `3b795bc5bd`, which folded the settings, routing, and save-time publication portions of `ef4dc9228a` and `0c11090d7c`. Background active-thread publication, retry, ticket refresh, and persistence history landed with `desktop restore Hyprnav runtime orchestration`. The fork's `/settings/projects/$environmentId/$projectId` route and its "Configure" button are replaced by the in-page section and search-param navigation.
